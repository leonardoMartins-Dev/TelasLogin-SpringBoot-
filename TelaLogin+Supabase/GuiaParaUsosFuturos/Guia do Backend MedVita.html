Como sair das telas prontas e chegar em classes, banco, regras e páginas funcionando: o método genérico, aplicado do começo ao fim ao sistema hospitalar.

Como usar este guia

Este guia ensina a construir o backend de um sistema com Spring Boot e MongoDB, do banco até a tela. Ele tem duas camadas ao mesmo tempo:

  • O método, que serve para qualquer projeto: como sair de um conjunto de telas e chegar nas classes, onde cada arquivo mora, como as camadas conversam e em que ordem construir.
  • O exemplo completo, o MedVita: as classes ProfissionalSaude, Paciente, Consulta, Internacao, Quarto e HistoricoMedico, com atributos, métodos, repositórios, services, controllers e as mudanças nas suas páginas.

Todo o código Java deste guia vem de um projeto de referência completo, escrito junto com o texto. Ele foi compilado para conferir que as classes se encaixam, e as regras das classes de modelo (lotar um quarto, cancelar uma consulta, dar alta, validar CPF) foram testadas. Ele ainda não foi executado ligado a um MongoDB de verdade: se algo falhar ao subir, a mensagem de erro do Spring costuma dizer exatamente qual classe e qual linha. Os trechos mostram o número de linha real de cada arquivo, e no fim de cada classe há um botão para ver o arquivo inteiro.

O guia parte do projeto que você mandou: Spring Boot 3.3.5, Java 17, Thymeleaf, o login com reCAPTCHA e as páginas de admin, médico e paciente. Se algo de Java ou Spring básico parecer estranho (anotação, construtor, lambda, @Controller, Model), o guia anterior, do TelaLogin, explica essas peças.

A receita: das telas às classes

O erro mais comum é começar pelo banco de dados ou pelas anotações. O caminho mais seguro é o contrário: começar pelo que o usuário vê. As telas dizem quais dados o sistema precisa guardar e quais ações ele precisa fazer. Esta é a receita, e ela vale para um hospital, uma loja, uma biblioteca ou uma academia.

Passo 1: para cada tela, anote o que ela mostra e o que ela envia

Suas páginas já estão prontas, com dados de exemplo escritos à mão. Isso é ótimo: cada coluna de tabela e cada campo de formulário é um dado que o back vai precisar fornecer ou receber.

Passo 2: substantivos viram classes, verbos viram métodos

Leia a tabela e sublinhe os substantivos que têm vida própria: médico (profissional de saúde), paciente, consulta, internação, quarto, histórico. Esses são os candidatos a classe. Os atributos saem das colunas: a tela de quartos mostra número, andar, capacidade e ocupação, então Quarto tem numero, andar, capacidadeMaxima e ocupacaoAtual.

Depois sublinhe os verbos: cancelar consulta, dar alta, ocupar leito, desativar médico, agendar. Eles viram métodos. A pergunta que decide onde cada método mora:

  • Se a regra só precisa dos dados do próprio objeto, o método fica na classe de modelo. "Um quarto lotado não aceita mais pacientes" só depende de ocupacaoAtual e capacidadeMaxima, então vira quarto.ocuparLeito().
  • Se a regra precisa consultar o banco ou coordenar vários objetos, o método fica num service. "O médico já tem consulta nesse horário?" precisa procurar outras consultas no banco, então vira ConsultaService.agendar(...).

Passo 3: descubra os estados

Toda palavra que aparece num badge colorido é um estado: Agendada, Realizada, Cancelada; Internado, Alta; Disponível, Ocupado, Lotado. Estados viram enum. Os estados também mostram as transições: uma consulta vai de Agendada para Realizada ou Cancelada, e nunca volta. Essas transições são regras que a classe deve proteger.

Passo 4: descubra o que identifica cada coisa

O que não pode se repetir? O CPF do paciente, o registro (CRM) do médico, o número do quarto, o e-mail de login. Isso vira índice único no banco e uma verificação no service.

Passo 5: descubra as relações

Uma consulta é de um paciente com um profissional. Uma internação é de um paciente, num quarto, com um responsável. Um paciente tem um histórico. Para cada relação, você decide se embute um objeto dentro do outro ou se guarda só uma referência (o id). A seção de MongoDB explica como decidir.

Passo 6: construa de baixo para cima, testando cada camada

Modelo → repositório → service → controller → página. Uma entidade de cada vez, começando pela mais simples (Quarto), para ver o ciclo inteiro funcionando cedo.

A receita em uma frase

Telas → dados e ações → classes (substantivos), métodos (verbos), enums (estados), índices únicos (o que não se repete), relações (embutir ou referenciar) → constrói de baixo para cima, uma entidade por vez.

Arquitetura: camadas e pastas

Um backend organizado em camadas tem uma regra simples: cada camada só conversa com a vizinha de baixo. Isso deixa cada peça pequena, fácil de testar e fácil de trocar.

  1. Página templates/O HTML com Thymeleaf. Mostra os dados que vieram no Model e envia formulários.
  2. Controller controller/Recebe a requisição, confere o formato do formulário, chama um service e escolhe a página ou o redirecionamento.
  3. Service service/As regras de negócio. Busca os objetos, aplica as regras, salva e dispara efeitos (histórico, e-mail).
  4. Repository repository/Interfaces que o Spring implementa sozinho. Buscam e gravam documentos.
  5. MongoDBGuarda os documentos nas coleções pacientes, consultas, quartos...

Atravessando todas as camadas: model/, as classes do domínio (Paciente, Consulta...), que todas usam, e form/, os objetos que levam os dados dos formulários da página até o controller.

Quem pode chamar quem:

  • Controller chama service. Nunca chama repository direto (senão a regra de negócio acaba espalhada pelos controllers).
  • Service chama repository e outros services. Nunca conhece Model, HTML ou HttpServletRequest.
  • Repository só fala com o banco.
  • As classes de modelo são usadas por todos, mas não chamam ninguém: não conhecem repository, service nem Spring MVC.

A estrutura de pastas do MedVita

Repare que existem dois estilos de organização misturados, de propósito:

  • As pastas model, repository, service, controller e form separam por camada (tipo de arquivo). É o jeito mais comum em projetos acadêmicos e fácil de navegar.
  • A pasta auth separa por funcionalidade: tudo do login fica junto, de todas as camadas. Isso é o que permite copiar o login para outro projeto de uma vez, que é exatamente o que você quer fazer.

Mova a classe principal para a raiz do pacote

Hoje a classe principal está em com.example.MedVita.application e usa scanBasePackages para encontrar as outras classes. Isso funciona para @Service e @Controller, mas não funciona para os repositories do MongoDB: o Spring Boot só procura repositories no pacote da classe principal e abaixo dele, e ignora o scanBasePackages. O sintoma é um erro na inicialização dizendo que não existe bean do tipo PacienteRepository.

A correção é mover a classe para com.example.MedVita (a raiz), renomear para MedVitaApplication e tirar o scanBasePackages. Assim tudo fica "abaixo" dela e o Spring acha tudo sozinho.

Lembre de atualizar também a classe de teste: com a classe principal na raiz, o @SpringBootTest a encontra sozinho e o classes = ... pode sair.

MongoDB em 15 minutos

O MongoDB é um banco de documentos. Em vez de tabelas com linhas e colunas fixas, ele guarda documentos parecidos com JSON, agrupados em coleções.

O que cada parte revela:

  • _id é gerado pelo MongoDB na primeira gravação. É um ObjectId, um código de 24 caracteres. No Java ele aparece como o atributo String id.
  • Os enums viram texto: "CARDIOLOGIA", "AGENDADA".
  • Datas viram ISODate e são guardadas em UTC (horário de Greenwich). A consulta das 14:30 em Brasília aparece como 17:30Z. O Spring converte de volta para o horário local quando lê, então no Java e nas telas continua 14:30. Só estranhe se abrir o banco direto.
  • Campos com valor null não são gravados. Por isso observacoesMedicas nem aparece: a consulta ainda não foi realizada.
  • _class é colocado pelo Spring Data com o nome da classe Java. Ele usa isso para saber que classe montar na leitura. Pode ignorar.

Embutir ou referenciar

Esta é a decisão mais importante de modelagem no MongoDB. Quando uma coisa se relaciona com outra, você tem duas opções:

  • Embutir: guardar o objeto inteiro dentro do outro documento, como um campo. Exemplo: os registros do histórico ficam dentro do documento HistoricoMedico, numa lista.
  • Referenciar: guardar só o id do outro documento. Exemplo: a consulta guarda pacienteId, e o paciente fica na coleção pacientes.
Pergunta Se a resposta for sim Exemplo no MedVita

Copiar alguns campos: a "fotografia"

Como não há JOIN, mostrar a agenda do médico com o nome de cada paciente exigiria uma busca extra por linha. A solução comum no MongoDB é guardar o id e também uma cópia dos campos que a tela mostra. Por isso a Consulta tem pacienteId e pacienteNome, profissionalId, profissionalNome e especialidade.

Isso tem um preço: se o paciente mudar de nome, as consultas antigas continuam com o nome antigo. Para consultas e internações isso é até desejável, porque é um registro do que aconteceu naquele dia (como um documento assinado). Se o dado mudar muito e precisar estar sempre atualizado, prefira só o id e busque na hora.

Regra prática para qualquer projeto

Referencie entidades com tela própria. Embuta listas pequenas que só existem dentro do pai. Copie para dentro da referência só os campos que as listagens mostram e que quase nunca mudam.

Índices

Um índice deixa as buscas por um campo rápidas e, se for único, impede valores repetidos. No MedVita: e-mail do usuário, CPF do paciente, registro do médico e número do quarto são únicos. pacienteId e profissionalId nas consultas têm índice comum, porque as telas buscam por eles o tempo todo.

Transações

No MongoDB, gravar um documento é sempre "tudo ou nada". Gravar dois documentos juntos com garantia de "tudo ou nada" (uma transação) só funciona quando o MongoDB roda como replica set (o Atlas, o serviço na nuvem, já roda assim; uma instalação local simples, não). O MedVita foi desenhado para não depender disso: quase toda ação grava um documento só. Onde grava dois (internar mexe no quarto e cria a internação), o guia mostra como proteger.

Modelagem: o diagrama de classes

Aplicando a receita às suas telas, chega-se a este diagrama. Ele serve também para a pasta DOCUMENTOS/DiagramaUML do trabalho.

Como ler o diagrama:

  • - é private (atributo), + é public (método). O tipo vem antes do nome no atributo e depois dos parênteses no método (o tipo de retorno). O $ marca um método static.
  • A seta com triângulo vazio (Pessoa <|-- Paciente) é herança: Paciente extends Pessoa.
  • O losango cheio (*--) é composição: o registro não existe fora do histórico. No MongoDB, composição quase sempre vira objeto embutido.
  • As setas simples são associações: a consulta conhece o paciente (pelo pacienteId). Os números nas pontas são as cardinalidades: um paciente tem de zero a muitas consultas (0..*), cada consulta tem exatamente um paciente (1).
  • Os atributos de fotografia (pacienteNome, profissionalNome, quartoDescricao) e os ids das referências foram omitidos do diagrama para ele ficar legível. Eles aparecem no código.

Por que Usuario e Paciente são classes separadas?

Login e dados de domínio são assuntos diferentes. O admin tem login e não é paciente nem médico. Um médico pode perder o acesso (conta desativada) e continuar aparecendo nas consultas antigas. E, separando, a classe Usuario pode ir para outro projeto sem levar nada de hospital junto. A ligação entre os dois é o perfilId (o id do paciente ou do profissional) e o e-mail, que é o mesmo nos dois.

Três convenções usadas em todas as classes de modelo

Todas as classes do model seguem o mesmo molde. Entender as três regras abaixo faz o resto do código ficar previsível.

  1. Construtor protected sem argumentos, só para o Spring Data. Quando o Spring lê um documento do banco, ele precisa criar o objeto vazio e depois preencher os campos. Esse construtor existe só para isso; protected impede que o seu código use ele por engano e crie um objeto pela metade.
  2. Construtor public com os dados obrigatórios, para o seu código. É ele que garante que todo objeto novo nasce válido: normaliza e-mail, define o status inicial, recusa capacidade zero.
  3. Métodos de comportamento não começam com get nem is. O Spring Data e o Thymeleaf tratam métodos getAlgo() como se existisse um atributo "algo". Um método calculado como getIdade() poderia ser gravado no banco como um campo idade que envelhece. Por isso os métodos calculados se chamam calcularIdade(), temVaga(), situacaoAtual(). Os get e is ficam só para os atributos de verdade.

Getters sim, setters só quando fizer sentido

Todo atributo tem get. Mas set só existe quando o valor pode mesmo ser trocado livremente (o telefone, por exemplo). O status de uma consulta não tem setStatus: ele só muda pelos métodos cancelar() e realizar(), que conferem se a mudança é permitida. É isso que o professor de Programação Modular chama de encapsulamento: o objeto protege as próprias regras.

Enums: os estados e as listas fixas

Tudo o que é uma lista fechada de opções vira enum: especialidades, status de consulta, status de internação, situação do quarto, tipo de registro e papel de usuário.

  • CLINICA_GERAL, CARDIOLOGIA... são as constantes: os únicos valores possíveis. Não existe new Especialidade(...) fora do enum.
  • ("Clínica Geral") chama o construtor do enum para aquela constante. O construtor de um enum é sempre privado.
  • No banco fica o nome da constante ("CLINICA_GERAL"), que nunca muda. Na tela aparece a descricao ("Clínica Geral"), que pode ter acento e espaço. Se um dia vocês quiserem escrever "Clínico Geral", muda só a descrição e os dados antigos continuam válidos.

Os enums de status guardam também a classe CSS do badge que as suas páginas já usam (badge-info, badge-success, badge-danger). Assim o template não precisa de um if para cada status: ele escreve th:classappend="${consulta.status.badge}". É uma pequena mistura de visual com modelo, aceita porque simplifica muito o HTML. A alternativa "pura" é um th:switch no template.

StatusInternacao (ATIVA "Internado", ALTA "Alta") e SituacaoQuarto (DISPONIVEL, OCUPADO, LOTADO) seguem o mesmo modelo. TipoRegistro (CONSULTA, INTERNACAO, EXAME) e Papel (ADMIN, MEDICO, PACIENTE) são enums simples, sem descrição.

Mais especialidades sem mexer em código

Se o hospital precisar cadastrar especialidades novas pela tela, o enum deixa de servir (ele é fixo no código). Aí Especialidade vira uma classe com coleção própria e uma tela de cadastro no admin. Para um trabalho acadêmico, o enum é a escolha certa.

  • Pessoa não tem @Document, então não tem coleção própria. Os campos dela são gravados dentro do documento de cada filha: um paciente no banco tem nome, email, telefone e também cpf, dataNascimento, endereco.
  • @Id: este atributo é o _id do documento. Como é String e começa null, o MongoDB gera um ObjectId no primeiro save e o Spring coloca o valor de volta no objeto.
  • @Indexed(unique = true): cria um índice único na coleção de cada filha. Dois pacientes com o mesmo e-mail causam erro no banco.
  • @CreatedDate: preenchido sozinho no primeiro save (precisa do @EnableMongoAuditing). Instant é um instante exato no tempo, sem fuso.

Os dois construtores são protected porque só as filhas os chamam (com super(...)). O segundo normaliza os dados na entrada: tira espaços do nome e deixa o e-mail em minúsculas. Isso importa porque o e-mail é usado para achar a pessoa depois; sem normalizar, Leo@Email.com e leo@email.com seriam pessoas diferentes.

  • split("\\s+") quebra o nome nos espaços (\\s+ é "um ou mais espaços") e devolve um array. [0] pega o primeiro pedaço: "Camila" de "Camila Souza".
  • inicial() é o que o avatar da barra lateral mostra. Hoje os templates calculam isso com #strings.substring(usuario, 0, 1); com o objeto na tela, basta ${paciente.inicial()}.

  • O laço roda duas vezes: posicao = 9 confere o primeiro dígito verificador e posicao = 10 confere o segundo. Cada dígito é multiplicado por um peso decrescente (10, 9, 8... para o primeiro; 11, 10, 9... para o segundo), a soma vezes 10 é dividida por 11, e o resto é o dígito esperado (resto 10 vira 0).

package com.example.MedVita.util;

public final class Cpf {

    private Cpf() {
    }

    public static String somenteDigitos(String cpf) {
        return cpf == null ? "" : cpf.replaceAll("\\D", "");
    }

    public static String formatar(String cpf) {
        String d = somenteDigitos(cpf);
        if (d.length() != 11) {
            return cpf;
        }
        return d.substring(0, 3) + "." + d.substring(3, 6) + "."
                + d.substring(6, 9) + "-" + d.substring(9);
    }

    public static boolean valido(String cpf) {
        String d = somenteDigitos(cpf);
        if (d.length() != 11 || d.chars().distinct().count() == 1) {
            return false;
        }
        for (int posicao = 9; posicao < 11; posicao++) {
            int soma = 0;
            for (int i = 0; i < posicao; i++) {
                soma += (d.charAt(i) - '0') * (posicao + 1 - i);
            }
            int digito = (soma * 10) % 11;
            if (digito == 10) {
                digito = 0;
            }
            if (digito != d.charAt(posicao) - '0') {
                return false;
            }
        }
        return true;
    }
}

model/Quarto.java

Quarto

O quarto é o melhor exemplo de classe que protege a própria regra: ele nunca deixa a ocupação passar da capacidade nem ficar negativa.

  • numero é String e não int porque número de quarto é um rótulo, não uma quantidade: pode ser "204A", e ninguém soma números de quarto.
  • @Version: controle de concorrência. O Spring guarda um contador em versao e soma 1 a cada save. Ao salvar, ele confere se o número no banco ainda é o mesmo de quando o objeto foi lido. A seção do InternacaoService mostra por que isso importa.

O construtor valida antes de atribuir. Se a capacidade for inválida, a exceção impede que o objeto exista. Isso é o que torna impossível ter um Quarto inválido em qualquer parte do programa.

Repare que não existe setOcupacaoAtual(int). A única forma de mudar a ocupação é ocuparLeito() e liberarLeito(), e as duas conferem a regra antes. ++ e -- somam e subtraem 1.

A situação não é gravada no banco: é derivada da ocupação. Se fosse um atributo, poderia ficar contraditória (situação "Disponível" com ocupação 4 de 4). A regra de derivação reproduz exatamente os exemplos da sua tela: 0 ocupados é Disponível, parte ocupada é Ocupado, cheio é Lotado. descricao() gera o texto "204 (2º andar)" usado em internações e no histórico.

model/Consulta.java

Consulta

A consulta tem um ciclo de vida: nasce Agendada e termina Realizada ou Cancelada. A classe garante que ninguém pula etapas.

  • pacienteId e profissionalId são as referências; @Indexed (sem unique) acelera as buscas "consultas deste paciente" e "agenda deste médico".
  • pacienteNome, profissionalNome e especialidade são a fotografia: permitem mostrar a agenda sem buscar paciente e médico linha por linha.
  • LocalDateTime junta data e horário num campo só, o que facilita comparar ("é depois de agora?") e ordenar.
  • observacoesPaciente vem do formulário de agendamento; observacoesMedicas é escrita pelo médico ao realizar a consulta e vai para o histórico.

O construtor recebe os objetos Paciente e ProfissionalSaude inteiros, não os ids soltos. Assim é impossível criar uma consulta com um nome que não bate com o id: os dois saem do mesmo objeto. A especialidade também vem do profissional, não do formulário, então ninguém marca "Cardiologia" com um ortopedista. E o status inicial é sempre AGENDADA.

Estas são as transições de estado. As duas partem de AGENDADA: não dá para cancelar uma consulta realizada nem realizar uma cancelada. Isso é uma máquina de estados simples, e é uma ótima coisa para desenhar no diagrama de estados do trabalho.

  • podeSerCancelada() é usado pelo template para decidir se mostra o botão Cancelar, e pelo service antes de cancelar. A mesma regra nos dois lugares, escrita uma vez só.
  • pertenceAoPaciente e pertenceAoProfissional são as verificações de dono, usadas pelos services para impedir que alguém mexa na consulta de outra pessoa.

A internação segue o mesmo desenho da consulta: fotografia dos envolvidos, status inicial garantido pelo construtor e uma transição (dar alta).

  • adicionarAlergia ignora texto vazio e repetido.

UsuarioRepository

Uma interface sem nenhuma implementação escrita por você. O Spring cria a classe de verdade quando o programa inicia, lendo os nomes dos métodos. A seção de repositories explica como isso funciona.

UsuarioDetailsService: a ponte entre o banco e o Spring Security

Esta é a peça que substitui o InMemoryUserDetailsManager. No login, o Spring Security chama loadUserByUsername com o que foi digitado no campo username, e espera receber um UserDetails (nome, senha criptografada, papéis). Aqui:

  • implements UserDetailsService: a classe assina o contrato que o Spring Security conhece. Como é um @Service e é a única que implementa esse contrato, o Spring Security passa a usá-la sozinho. Não precisa registrar em lugar nenhum.
  • findByUsername(...) devolve um Optional<Usuario>, uma "caixa" que pode estar vazia. .orElseThrow(...) abre a caixa ou, se estiver vazia, lança a exceção que o Spring espera para "usuário não existe".
  • usuario.getPapel().name() transforma o enum Papel.MEDICO no texto "MEDICO". O .roles(...) acrescenta o prefixo e o papel vira ROLE_MEDICO.
  • .disabled(!usuario.isAtivo()): conta desativada não entra, mesmo com a senha certa.

A comparação da senha continua sendo feita pelo Spring Security, com o BCryptPasswordEncoder, exatamente como no TelaLogin.

UsuarioService

Faz o que o antigo UserService fazia, agora com o banco: criar recusa e-mail repetido, criptografa a senha e salva. repository.save(obj) grava e devolve o objeto já com o id preenchido pelo MongoDB. Os outros métodos (buscarPorEmail, trocarSenha, desativar) seguem o mesmo padrão: buscar, chamar o método do objeto, salvar.

package com.example.MedVita.auth;

import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Service;

import com.example.MedVita.exception.RecursoNaoEncontradoException;
import com.example.MedVita.exception.RegraNegocioException;

@Service
public class UsuarioService {

    private final UsuarioRepository usuarioRepository;
    private final PasswordEncoder passwordEncoder;

    public UsuarioService(UsuarioRepository usuarioRepository, PasswordEncoder passwordEncoder) {
        this.usuarioRepository = usuarioRepository;
        this.passwordEncoder = passwordEncoder;
    }

    public Usuario criar(String email, String senha, String nome, Papel papel, String perfilId) {
        if (existe(email)) {
            throw new RegraNegocioException("Já existe uma conta com o e-mail " + email + ".");
        }
        Usuario usuario = new Usuario(email, passwordEncoder.encode(senha), nome, papel, perfilId);
        return usuarioRepository.save(usuario);
    }

    public boolean existe(String email) {
        return usuarioRepository.existsByUsername(normalizar(email));
    }

    public Usuario buscarPorEmail(String email) {
        return usuarioRepository.findByUsername(normalizar(email))
                .orElseThrow(() -> new RecursoNaoEncontradoException("Usuário não encontrado."));
    }

    public void trocarSenha(String email, String novaSenha) {
        Usuario usuario = buscarPorEmail(email);
        usuario.trocarSenha(passwordEncoder.encode(novaSenha));
        usuarioRepository.save(usuario);
    }

    public void desativar(String email) {
        Usuario usuario = buscarPorEmail(email);
        usuario.desativar();
        usuarioRepository.save(usuario);
    }

    private String normalizar(String email) {
        return email.trim().toLowerCase();
    }
}

Tokens de recuperação que expiram sozinhos

@Indexed(expireAfterSeconds = 900) cria um índice TTL (time to live): o próprio MongoDB apaga cada token 900 segundos (15 minutos) depois do horário gravado em criadoEm. Antes, os tokens ficavam num HashMap e sumiam quando o programa reiniciava; agora ficam no banco e se limpam sozinhos.

O MongoDB verifica os índices TTL a cada minuto, então um token pode sobreviver alguns segundos além da validade. Por isso o método expirado() confere a hora exata também. static final em VALIDADE cria uma constante da classe, compartilhada por todos os objetos.

emailDoToken encadeia operações no Optional: procura o token, descarta se estiver expirado (filter) e troca o token pelo e-mail dele (map). Se qualquer etapa ficar vazia, o resultado é um Optional vazio, que o controller trata como "link inválido". Isso substitui os if (x == null) return null; da versão anterior.

SecurityConfig: regras por papel

Um mapa de papel para a página inicial. Map.of(chave, valor, chave, valor...) cria um mapa que não pode ser alterado. Num projeto novo, é só trocar as linhas.

  • requestMatchers aceita vários caminhos de uma vez. Sem HttpMethod, a regra vale para GET e POST, então as linhas duplicadas da versão anterior viram uma.
  • No projeto atual, /paciente/** só exigia estar logado: um médico conseguia abrir as páginas do paciente. Agora cada área exige o seu papel.

Em vez de um if/else if por papel, uma stream: pega os papéis do usuário (ROLE_MEDICO), troca cada um pela página do mapa (/medico), descarta os que não estão no mapa (filter(Objects::nonNull)) e fica com o primeiro. Com um papel novo, o código não muda; só o mapa. A falha de login agora volta para a tela de login com ?erro=credenciais; acrescente no login.html um <div th:if="${param.erro}">Usuário ou senha inválidos.</div>.

O bean InMemoryUserDetailsManager sai do SecurityConfig. O PasswordEncoder continua. O Spring Security encontra sozinho o UsuarioDetailsService e o PasswordEncoder e liga os dois ao login.

package com.example.MedVita.auth;

import java.util.Map;
import java.util.Objects;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configuration.EnableWebSecurity;
import org.springframework.security.core.GrantedAuthority;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.security.web.authentication.UsernamePasswordAuthenticationFilter;

@Configuration
@EnableWebSecurity
public class SecurityConfig {

    // Página inicial de cada papel: é o que muda de um projeto para outro
    private static final Map<String, String> PAGINA_INICIAL = Map.of(
            "ROLE_ADMIN", "/admin",
            "ROLE_MEDICO", "/medico",
            "ROLE_PACIENTE", "/home");

    private final RecaptchaFilter recaptchaFilter;

    public SecurityConfig(RecaptchaService recaptchaService) {
        this.recaptchaFilter = new RecaptchaFilter(recaptchaService);
    }

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/login/**", "/register", "/recoverpassword",
                        "/resetpassword", "/error", "/css/**", "/images/**").permitAll()
                .requestMatchers("/admin/**").hasRole("ADMIN")
                .requestMatchers("/medico/**").hasRole("MEDICO")
                .requestMatchers("/home", "/paciente/**").hasRole("PACIENTE")
                .anyRequest().authenticated()
            )
            .addFilterBefore(recaptchaFilter, UsernamePasswordAuthenticationFilter.class)
            .formLogin(form -> form
                .loginPage("/login")
                .permitAll()
                .successHandler((request, response, authentication) -> {
                    String destino = authentication.getAuthorities().stream()
                            .map(GrantedAuthority::getAuthority)
                            .map(PAGINA_INICIAL::get)
                            .filter(Objects::nonNull)
                            .findFirst()
                            .orElse("/login?erro=papel");
                    response.sendRedirect(destino);
                })
                .failureHandler((request, response, exception) ->
                    response.sendRedirect("/login?erro=credenciais"))
            )
            .logout(logout -> logout
                .logoutUrl("/logout")
                .logoutSuccessUrl("/login?logout=true")
                .permitAll()
            );

        return http.build();
    }

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}

Repositories: falando com o banco sem escrever consultas

Um repository é uma interface que estende MongoRepository<Classe, TipoDoId>. Você não escreve a implementação: o Spring gera uma classe que faz as consultas ao MongoDB e a registra como bean. Qualquer service pode recebê-la no construtor.

Métodos que já vêm prontos

Só por estender MongoRepository, todo repository ganha:

Método O que faz
save(obj) Se id for null, insere e preenche o id. Se tiver id, substitui o documento inteiro
saveAll(lista) O mesmo para vários
findById(id) Devolve Optional<T>: vazio se não existir
findAll() Todos os documentos da coleção
existsById(id) true ou false
count() Quantos documentos existem
deleteById(id), delete(obj) Apaga

save substitui o documento inteiro

save não atualiza "só um campo": ele grava o objeto inteiro por cima do que estava no banco. Por isso o padrão em todo service é buscar o objeto, mudar o que precisa e salvar. Se você criar um objeto novo com o mesmo id e só alguns campos preenchidos, os outros campos serão apagados.

Consultas pelo nome do método

Para buscas específicas, você declara um método com um nome que segue uma gramática. O Spring lê o nome e monta a consulta ao MongoDB:

Palavra no nome Exemplo no MedVita Consulta gerada
findBy + campo findByEmail(String email) email igual ao valor
existsBy existsByCpf(String cpf) existe algum? devolve boolean
countBy countByStatus(StatusInternacao s) quantos? devolve long
deleteBy deleteByToken(String token) apaga os que casam
And, Or findByEspecialidadeAndAtivoTrue... combina condições
True, False findByAtivoTrueOrderByNomeAsc() campo booleano verdadeiro (sem parâmetro)
Between countByDataHoraBetweenAndStatus(inicio, fim, s) entre dois valores (sem incluir as pontas)
After, Before ...AndDataHoraAfter(agora) depois ou antes
Containing + IgnoreCase findByNomeContainingIgnoreCase(...) contém o texto, ignorando maiúsculas
OrderBy...Asc/Desc findByPacienteIdOrderByDataHoraDesc ordenação
findFirstBy findFirstByPacienteIdAndStatusAndDataHoraAfterOrderByDataHoraAsc só o primeiro resultado
findAllByOrderBy findAllByOrderByNomeAsc() todos, ordenados (repare no By antes do OrderBy)

Os parâmetros entram na ordem em que os campos aparecem no nome. O tipo de retorno também decide o comportamento: List<T> para vários, Optional<T> para zero ou um, boolean para exists, long para count.

O nome do campo tem que ser o nome do atributo

findByDataHora só funciona porque a classe Consulta tem um atributo chamado dataHora. Um erro de digitação (findByDatahora) não compila como erro: o programa quebra ao iniciar, com uma mensagem dizendo que a propriedade datahora não existe. Se o projeto não subir depois de criar um repository, leia essa mensagem primeiro.

Os repositories do MedVita

Cada método existe porque alguma tela ou regra precisa dele:

  • findByPacienteIdOrderByDataHoraDesc: "Minhas Consultas", da mais recente para a mais antiga.
  • findByProfissionalIdAndDataHoraBetween...: agenda do médico filtrada por dia (do início do dia até o início do dia seguinte).
  • existsByProfissionalIdAndDataHoraAndStatus: "o médico já tem consulta agendada nesse horário?", a regra anti-conflito do agendamento.
  • findFirstBy...DataHoraAfterOrderByDataHoraAsc: a próxima consulta agendada do paciente, para o card do painel.

Essa é a mesma linguagem de consulta que você usa no filtro do MongoDB Compass.

service/ · exception/

Services: onde moram as regras de negócio

Um service é uma classe @Service com um método para cada ação que as telas oferecem: agendar consulta, cancelar consulta, internar, dar alta, cadastrar médico. Ele junta os objetos do banco, aplica as regras e salva.

Quase todo método de service segue os mesmos cinco passos. Vale decorar, porque serve para qualquer projeto:

  1. Buscar os objetos envolvidos (pelos repositories ou por outros services).
  2. Validar as regras que dependem do banco ou de vários objetos (horário já ocupado? CPF repetido? paciente já internado?).
  3. Chamar os métodos dos objetos, que aplicam as regras deles mesmos (quarto.ocuparLeito(), consulta.cancelar()).
  4. Salvar o que mudou.
  5. Disparar os efeitos colaterais (registrar no histórico, mandar e-mail).

As exceções do projeto

Quando uma regra é quebrada, o service lança uma exceção com uma mensagem pronta para mostrar ao usuário. O projeto tem duas:

  • RegraNegocioException: o usuário pediu algo que as regras não permitem ("Esse horário já está ocupado"). O controller pega essa exceção e mostra a mensagem na tela.
  • RecursoNaoEncontradoException: o id pedido não existe ("Consulta não encontrada"). Normalmente vira a página de erro com status 404.

As duas herdam de RuntimeException, então não precisam de throws em cada método: sobem livremente do modelo até o controller. As mensagens são escritas para o usuário final, em português claro, porque é exatamente o texto que vai aparecer na tela.

Onde cada validação mora

  • Formato do dado (campo vazio, e-mail inválido, data no passado): anotações no formulário (@NotBlank, @Email, @Past). Seção de formulários.
  • Regra de um objeto só (quarto lotado, consulta já cancelada): método da classe de modelo.
  • Regra que precisa do banco ou de vários objetos (horário ocupado, CPF repetido, dono da consulta): service.
  • Garantia final contra repetição: índice único no banco.

A tela do admin não tem campo de senha para o médico, e isso é correto: o admin não deve saber a senha de ninguém. A solução reaproveita o fluxo de recuperação de senha que vocês já têm:

service/ConsultaService.java

ConsultaService

O service mais completo do projeto. Ele mostra as regras de agendamento, as verificações de dono e as buscas das telas.

As regras de funcionamento viram constantes com nome. Se o hospital passar a abrir às 7h, muda uma linha, e o código que usa ABERTURA explica sozinho o que está conferindo.

Os cinco passos, na prática:

  1. Buscar: o paciente pelo e-mail de quem está logado; o profissional pelo id escolhido no select. O paciente nunca vem do formulário: se viesse, alguém poderia agendar em nome de outra pessoa trocando um campo escondido.
  2. Validar: o profissional está ativo? O horário é válido? O médico está livre? O paciente está livre? Só consultas AGENDADA ocupam horário; uma cancelada libera a vaga.
  3. LocalDateTime.of(data, horario) junta os dois campos do formulário (<input type="date"> e <input type="time">) num só.
  4. Criar a Consulta, que nasce AGENDADA com a fotografia dos nomes.
  5. Salvar e devolver.
  • Um método private que só valida: não devolve nada, apenas lança exceção se algo estiver errado. Separar isso deixa o agendar legível.
  • !hora.isBefore(FECHAMENTO) quer dizer "18:00 ou depois": a última consulta possível é 17:30.
  • % é o resto da divisão. Minuto 30 % 30 = 0 (ok); minuto 45 % 30 = 15 (recusado). Isso garante que duas consultas nunca se sobreponham pela metade, e é o que faz a checagem de conflito por horário exato funcionar.

Sempre confira o dono

O botão Cancelar envia um POST /paciente/consultas/{id}/cancelar. O id está na URL, e qualquer pessoa logada pode mudar esse id e tentar cancelar a consulta de outro paciente. A regra de segurança por papel (/paciente/** exige PACIENTE) não impede isso, porque o atacante também é paciente. A verificação pertenceAoPaciente é o que impede. Esse tipo de falha tem nome (IDOR, referência direta insegura a objeto) e está entre as mais comuns em sistemas web. Toda ação sobre um objeto específico precisa conferir se ele pertence a quem está pedindo.

O médico registra a consulta: confere o dono, muda o status pelo método da classe (que recusa se não estiver agendada), salva e, como efeito colateral, acrescenta a linha no prontuário do paciente.

Um extra que a tela de agendamento pode usar: gera todos os horários do dia de 30 em 30 minutos e tira os já ocupados. Set é uma coleção sem repetição com busca rápida (contains). O for com LocalTime funciona como um for com números: começa em 8:00, soma 30 minutos a cada volta e para antes das 18:00. A seção "Possibilidades a mais" mostra como ligar isso à tela.

                hoje.atStartOfDay(), hoje.plusDays(1).atStartOfDay(), StatusConsulta.AGENDADA);

        LocalDate hoje = LocalDate.now();
        return consultaRepository.countByProfissionalIdAndDataHoraBetweenAndStatus(

    }

    public List<LocalTime> horariosLivres(String profissionalId, LocalDate dia) {
        Set<LocalTime> ocupados = consultaRepository
                .agendaDoDia(profissionalId, dia.atStartOfDay(), dia.plusDays(1).atStartOfDay())
                .stream()
                .map(consulta -> consulta.getDataHora().toLocalTime())
                .collect(Collectors.toSet());

        List<LocalTime> livres = new ArrayList<>();
        for (LocalTime h = ABERTURA; h.isBefore(FECHAMENTO); h = h.plusMinutes(DURACAO_MINUTOS)) {
            LocalDateTime candidato = LocalDateTime.of(dia, h);
            if (!ocupados.contains(h) && candidato.isAfter(LocalDateTime.now())) {
                livres.add(h);
            }
        }
        return livres;
    }

    private void validarHorario(LocalDateTime dataHora) {
        if (!dataHora.isAfter(LocalDateTime.now())) {
            throw new RegraNegocioException("Escolha um horário no futuro.");
        }
        DayOfWeek dia = dataHora.getDayOfWeek();
        if (dia == DayOfWeek.SATURDAY || dia == DayOfWeek.SUNDAY) {
            throw new RegraNegocioException("Não há atendimento aos fins de semana.");
        }
        LocalTime hora = dataHora.toLocalTime();
        if (hora.isBefore(ABERTURA) || !hora.isBefore(FECHAMENTO)) {
            throw new RegraNegocioException("O atendimento é das 8h às 18h.");
        }
        if (hora.getMinute() % DURACAO_MINUTOS != 0) {
            throw new RegraNegocioException("Os horários são de 30 em 30 minutos (ex.: 14:00, 14:30).");
        }
    }

service/InternacaoService.java

InternacaoService

Internar mexe em dois documentos: cria a internação e ocupa um leito do quarto. Dar alta faz o contrário e ainda registra no histórico.

  • Um paciente não pode ter duas internações ativas ao mesmo tempo.
  • O responsável é o médico logado, não um campo do formulário.
  • quarto.ocuparLeito() lança exceção se o quarto estiver lotado. Repare que isso acontece antes de qualquer save: se falhar, nada foi gravado.
  • A Internacao também é construída antes de salvar o quarto, porque o construtor pode recusar a data de previsão. Só quando tudo está validado os dois documentos são gravados.

Dois médicos, um leito: para que serve o @Version

Imagine o quarto 204, com 1 leito livre. Dois médicos abrem a tela ao mesmo tempo e internam pacientes diferentes. Os dois leem o quarto com ocupação 0, os dois chamam ocuparLeito() (que passa, porque 0 < 1) e os dois salvam ocupação 1. Resultado: dois pacientes num quarto de um leito.

Com @Version, o primeiro save grava versão 6. O segundo tenta salvar um objeto lido na versão 5, o Spring percebe que alguém mudou o quarto no meio do caminho e lança OptimisticLockingFailureException em vez de gravar. Como o quarto é salvo antes da internação, a segunda internação nem chega a ser criada. O segundo médico vê a página de erro e tenta de novo, agora vendo o quarto lotado.

Mesma estrutura: mudar os dois objetos pelos seus métodos (que validam), salvar os dois e registrar no prontuário. O quartoId guardado na internação é o que permite achar o quarto certo na hora da alta.

Formulários e validação

No TelaLogin, cada campo do formulário virava um @RequestParam no controller. Com sete ou oito campos isso fica difícil de ler, e não há onde colocar as regras de formato. A solução é uma classe de formulário: um objeto simples com um atributo para cada campo da tela, que o Spring preenche sozinho.

  • Cada atributo corresponde a um campo do HTML com o mesmo nome (name="motivo" → motivo).
  • As anotações de jakarta.validation (do starter-validation) descrevem as regras de formato. message é o texto que aparece embaixo do campo quando a regra falha.
  • @NotBlank (texto não vazio, nem só espaços) é para String. Para datas, números e enums, que chegam null quando vazios, use @NotNull.
  • @DateTimeFormat ensina o Spring a converter o texto que o navegador manda. O <input type="date"> envia 2026-09-28 (formato ISO) e o <input type="time"> envia 14:30. Sem essa anotação, a conversão para LocalDate e LocalTime pode falhar.
  • A classe precisa de getters e setters para cada atributo (estão no arquivo completo): o Spring usa os setters para preencher o objeto e o Thymeleaf usa os getters para mostrar os valores de volta na tela.

Por que não receber direto um objeto Paciente ou Consulta?

Seria possível escrever @ModelAttribute Paciente paciente no controller. Mas aí qualquer campo da classe poderia vir da requisição: alguém poderia mandar um campo escondido ativo=false ou status=REALIZADA e o Spring preencheria. Além disso, a tela e a classe raramente batem: o cadastro tem senha, que não existe em Paciente; o agendamento tem data e horario separados, e a Consulta tem dataHora. O formulário é um objeto próprio da tela, com só os campos que ela pode enviar. O service traduz formulário em objeto de modelo.

Os cards do painel

Os quatro números que hoje estão escritos à mão no admin.html (3, --, 0, --) passam a vir do banco. No template: <div class="stat-value" th:text="${totalMedicos}">3</div>, e o mesmo para os outros três.

O GET de uma página com formulário coloca no Model um formulário vazio (o template precisa de um objeto para o th:object) e as listas que a página mostra.

Este é o molde de todo POST com formulário do projeto:

  • @ModelAttribute("form") ProfissionalForm form: o Spring cria um ProfissionalForm e chama um setter para cada campo do formulário cujo name bate com um atributo. O "form" é o nome com que ele fica no Model, o mesmo do th:object="${form}".
  • @Valid: depois de preencher, roda as anotações de validação.
  • BindingResult erros: onde ficam os erros encontrados. Ele tem que vir imediatamente depois do parâmetro validado. Se estiver em outra posição, o Spring lança uma exceção em vez de entregar os erros para você.
  • Com erros de formato, o método devolve o próprio template, sem redirecionar. Assim a página volta com o que a pessoa digitou e as mensagens embaixo de cada campo. Por isso carregarListas é chamado de novo: sem ele, a tabela de médicos viria vazia.
  • Sem erros, chama o service. Se uma regra de negócio falhar, a mensagem da exceção vira um recado.
  • redirect.addFlashAttribute("sucesso", ...) guarda um recado que sobrevive a exatamente um redirecionamento. Na página seguinte ele aparece no Model como ${sucesso} e depois some. É mais limpo que o ?cadastro=sucesso na URL do TelaLogin: não aparece no endereço e não volta se a pessoa recarregar a página.

Dado que vem no caminho da URL

{id} no mapeamento é uma variável de caminho. Para POST /admin/medicos/66f19f11.../desativar, o @PathVariable("id") entrega "66f19f11...". É o terceiro jeito de receber dados, ao lado do corpo do formulário e do ?parametro= da URL. Ações que mudam dados (remover, cancelar, dar alta) usam POST, nunca um link GET: links podem ser abertos por pré-carregamento do navegador, e o POST exige o token CSRF.

Com os usuários no banco, alguém precisa criar o primeiro admin (senão ninguém consegue cadastrar médicos). E para testar, é cômodo ter quartos e médicos de exemplo. Um CommandLineRunner roda uma vez, logo depois que o programa sobe.

  • @Component é a anotação genérica de "gerencie esta classe" (@Service e @Controller são versões dela com um significado a mais).
  • implements CommandLineRunner obriga a ter o método run, que o Spring Boot chama no fim da inicialização.
  • String... args (três pontos) é um parâmetro que aceita qualquer quantidade de valores; aqui não é usado.

Testes de service com Mockito

Um service depende de repositories, que dependem do banco. Para testar só a regra, o Mockito cria objetos falsos (mocks) no lugar das dependências, e você diz o que cada um deve responder.

  • @Mock cria um objeto falso de cada dependência. Por padrão, todos os métodos dele devolvem null, 0 ou false.
  • @InjectMocks cria o ConsultaService de verdade, passando os mocks no construtor.
  • when(...).thenReturn(true): "quando o service perguntar se o horário está ocupado, responda que sim". any() aceita qualquer valor naquele parâmetro; eq(...) exige aquele valor exato.
  • O teste confere que o agendamento é recusado e, com verify(..., never()).save(any()), que nada foi gravado. Sem MongoDB rodando, em milissegundos.
  • O método @BeforeEach do arquivo (roda antes de cada teste) prepara o paciente, o médico e um formulário para a próxima segunda-feira às 10h, um horário sempre válido.

A barra lateral em um arquivo só (fragmentos)

As seis páginas do paciente repetem a mesma barra lateral inteira. Uma mudança no menu exige editar seis arquivos. O Thymeleaf resolve com fragmentos:

O th:replace troca a tag pelo fragmento, passando qual item do menu deve ficar ativo. O mesmo vale para o bloco de mensagens e para as barras do médico e do admin.

Horários livres na tela de agendamento

O ConsultaService.horariosLivres(profissionalId, dia) já existe. Para a tela mostrar só os horários disponíveis quando o paciente escolhe médico e data, crie um endpoint que devolve JSON e chame-o com JavaScript:

@ResponseBody faz o método devolver os dados (convertidos em JSON pelo Jackson) em vez do nome de um template. Troque o <input type="time"> por um <select th:field="*{horario}">, que o script preenche. O mesmo truque serve para filtrar médicos pela especialidade escolhida no primeiro select.

E-mails de confirmação e lembrete

O SendEmailService já está pronto para ser reaproveitado. No fim do ConsultaService.agendar, um e-mail de confirmação para o paciente. Para lembretes, o Spring tem tarefas agendadas: @EnableScheduling numa classe de configuração e um método com @Scheduled(cron = "0 0 8 * * *") (todo dia às 8h) que busca as consultas do dia seguinte e manda um lembrete para cada paciente.

Perfis de desenvolvimento e produção

Crie application-dev.properties (banco local, DataSeeder com dados de exemplo) e application-prod.properties (Atlas, sem dados de exemplo). O perfil ativo é escolhido com spring.profiles.active=dev no application.properties ou na variável de ambiente SPRING_PROFILES_ACTIVE. Classes com @Profile("dev") só existem nesse perfil.

Logs no lugar de System.out.println

System.out.println não tem data, nível nem como ser desligado. O Spring Boot já traz o SLF4J:

Os {} são preenchidos pelos argumentos na ordem. Cuidado com dados de saúde nos logs: registre ids, não diagnósticos.

Cuidados de privacidade (LGPD)

Dados de saúde são dados pessoais sensíveis na LGPD, com regras mais rígidas. Para um trabalho acadêmico isso não muda o código, mas vale aplicar três hábitos:

  • Acesso mínimo: o paciente só vê os próprios dados (as verificações de dono dos services), e só o médico vê a ficha de outros pacientes.
  • Nada de dados reais: use nomes e CPFs inventados (o CPF 529.982.247-25 é um exemplo válido conhecido) e não suba o banco nem o .env para o Git.
  • Registro de acesso: num sistema real, cada abertura de ficha seria registrada (quem, quando, qual paciente). Seria uma coleção acessos com um documento por visualização.

API REST para outro front-end

Se um dia o front for React, Angular ou um aplicativo, as camadas de modelo, repository e service ficam exatamente como estão. Só os controllers mudam: @RestController no lugar de @Controller, recebendo e devolvendo JSON.

Esse é o maior benefício da separação em camadas: a regra de negócio não sabe se quem está do outro lado é uma página Thymeleaf ou um aplicativo de celular.

Lombok: menos getters escritos à mão

A biblioteca Lombok gera getters, setters e construtores a partir de anotações (@Getter, @Setter, @NoArgsConstructor). Ela encurta muito as classes de formulário. Para as classes de modelo, pense bem antes: escrever os getters à mão, e deixar de fora os setters que não devem existir, é justamente o que mostra encapsulamento no trabalho de Programação Modular.

Checklist para um projeto novo

Use esta lista como roteiro sempre que começar um sistema com Spring Boot e MongoDB. Entre parênteses, o que foi feito no MedVita.

Do zero ao sistema funcionando

  1. Liste as telas e, para cada uma, o que ela mostra e o que envia (a tabela da receita).
  2. Substantivos viram classes, colunas viram atributos, badges viram enums, ações viram métodos (Quarto, Consulta, ocuparLeito, StatusConsulta).
  3. Decida o que é único (índices) e o que embutir ou referenciar (CPF único; registros embutidos no histórico; consulta referencia paciente com fotografia do nome).
  4. Desenhe o diagrama de classes antes de programar.
  5. Configure o projeto: dependências, application.properties, .env, MongoDB rodando, classe principal na raiz, @EnableMongoAuditing.
  6. Copie a pasta auth de um projeto anterior e ajuste Papel, PAGINA_INICIAL e as regras de acesso.
  7. Crie as classes de modelo com construtor protegido sem argumentos, construtor público que valida, getters, e métodos de comportamento sem get. Teste os métodos com JUnit.
  8. Crie um repository por coleção, com os métodos que as telas pedem.
  9. Crie um service por entidade, um método por ação, seguindo: buscar, validar, chamar métodos do objeto, salvar, efeitos colaterais. Confira sempre o dono.
  10. Crie os formulários com validação.
  11. Crie um controller por área: GET mostra, POST age e redireciona com mensagem.
  12. Troque os dados de exemplo das páginas por th:each, th:text e th:object.
  13. Crie o DataSeeder com o admin e dados de exemplo.
  14. Teste os services mais importantes com Mockito.

Ordem sugerida para o MedVita

Construir tudo de uma vez é o jeito mais rápido de ter um projeto que não sobe e não se sabe por quê. Esta ordem faz cada etapa funcionar antes da próxima, e cada uma usa o que a anterior deixou pronto:

  1. MongoDB rodando, dependências, application.properties, classe principal na raiz, MongoConfig. Sobe sem erro?
  2. Pasta auth com usuários no banco e DataSeeder só com o admin. Consegue logar como admin?
  3. Quarto de ponta a ponta: modelo, repository, service, MedicoController só com quartos, página medico/quartos. É a entidade mais simples e mostra o ciclo inteiro.
  4. Profissional de saúde: cadastro e remoção pelo admin, com o e-mail de convite.
  5. Paciente: cadastro pela tela de registro, criando histórico e login. Consegue logar como paciente?
  6. Consulta: agendar, listar, cancelar (paciente); agenda e realizar (médico).
  7. Internação: internar e dar alta, conferindo a ocupação dos quartos.
  8. Histórico: a página do paciente e a ficha para o médico.
  9. Painéis com os números reais nos cards das três áreas.

Ao terminar cada etapa, faça um commit. Se algo quebrar na etapa seguinte, você sabe exatamente o que mudou.

Os trechos com nome de arquivo e número de linha vêm de um projeto de referência completo, escrito para este guia, compilado e com as regras de modelo testadas. Os trechos de HTML mostram como adaptar as páginas que você já tem.
